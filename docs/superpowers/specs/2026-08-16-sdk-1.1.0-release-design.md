# SDK v1.1.0 Release Preparation Design

## Goal

Prepare `web-sdk-pp-doclayoutv3@1.1.0` as the first minor SDK release containing per-class detection thresholds. The preparation must leave a reviewed, internally consistent release commit that is ready for the repository's existing tag-driven release workflow, without creating a tag, GitHub Release, or npm publication.

## Scope

- Update the SDK package version from `1.0.6` to `1.1.0`.
- Update the runtime SDK version constant and every checked-in contract or test fixture that intentionally asserts the current SDK version.
- Add a `1.1.0` changelog entry for the per-class threshold API and Demo editor.
- Verify that package metadata, runtime metadata, generated API documentation, and release checks agree on `1.1.0`.
- Perform the work on `codex/release-v1.1.0` and commit the completed preparation after verification.

The model manifest version remains `1.0.2`. Model manifests, ONNX assets, hashes, delivery URLs, and model-release tags are out of scope. The release workflow, Trusted Publishing configuration, public API behavior, and implementation of per-class thresholds must not change as part of this preparation.

## Version Sources

The canonical version changes are:

- `packages/sdk/package.json`: npm package version becomes `1.1.0`.
- `packages/sdk/src/model/manifest.ts`: `CURRENT_SDK_VERSION` becomes `1.1.0`.

Checked-in consumers that encode the current SDK version must be synchronized only where the value represents this release:

- the generated SDK API report;
- SDK manifest/version tests;
- Demo version assertions;
- release-verifier fixtures and expectations.

Before editing, all occurrences of `1.0.6` must be classified. Historical changelog entries, historical examples, tags, or fixtures that deliberately test another release stay unchanged. The lockfile does not currently embed the workspace package version and should remain unchanged unless the package manager demonstrates otherwise.

## Changelog

Add a dated `1.1.0` section to `CHANGELOG.md`. It records:

- the additive `classThresholds` option on `detect()`;
- the fallback order from a class override to the global threshold and then the default threshold;
- confidence-filter-only behavior, with the global threshold continuing to control mask binarization;
- the Demo's responsive per-class threshold editor.

The changelog must not claim a new model version or model asset release.

## Release Workflow

The existing `.github/workflows/release.yml` remains the publication mechanism. It accepts a pushed `v*` tag on `main`, validates the tag and package with `scripts/verify-release.mjs`, and publishes through npm Trusted Publishing with provenance.

This task stops before the workflow trigger. After local preparation is reviewed and merged separately, creating and pushing `v1.1.0` requires explicit confirmation. Creating a GitHub Release and verifying the public npm package are later release operations, not part of this design.

## Verification

Verification proceeds from focused checks to the full repository gate:

1. Search version-bearing files and confirm every live SDK release value is `1.1.0` while the model version remains `1.0.2`.
2. Run focused SDK manifest tests, Demo version assertions, and release-verifier tests.
3. Run the release verifier with the intended release name `v1.1.0`.
4. Run formatting, lint, type checking, complete tests, API extraction checks, and production builds using the repository's existing scripts.
5. Inspect the final diff and Git status to ensure no model assets, workflow files, unrelated user changes, tags, or generated noise are included.

On Windows, line-ending-only Prettier failures are checked again with the repository's established `--end-of-line auto` content check. This does not authorize reformatting unrelated files. Browser-test runner processes must be allowed to report all test results and then be stopped by their exact process ID if the known Windows orphan-process behavior occurs.

Any version mismatch, unexpected lockfile change, failed test, or release-verifier failure blocks the release commit until its cause is understood and resolved.

## Commit And Safety Boundary

The design document is committed separately before implementation. The release preparation then receives its own focused commit on `codex/release-v1.1.0`. No remote branch push, pull request, merge, tag, GitHub Release, npm publish, or model asset mutation is performed without a later explicit instruction.
